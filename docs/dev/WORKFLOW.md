# 開発ワークフロー

このプロジェクトでの AI の動き方の詳細。入口はルート `CLAUDE.md` の「開発ループ」。

## 全体の流れ

```
依頼
 ├─ 機能追加・改修 → ① 仕様 → ② 実装 → ③ QA → ④ 出荷
 ├─ バグ修正 ─────→ ⓪ 再現・原因確定 → ①（凍結書に再現手順と原因を書く）→ ② → ③ → ④
 ├─ 雑務 ────────→ ② → ③（軽量）→ ④
 └─ 質問・調査 ───→ 回答して終了（勝手に直さない）
```

## ① 仕様（spec-freeze）

- 仕様の解釈が 2 通り以上ありうるなら spec-freeze スキルを使う。分かれ道ゼロの自明な変更はスキップしてよい
- 凍結書は `docs/spec/YYYY-MM-DD-機能名.md` に保存する
- 凍結書の「合格ライン」が書けないうちは実装に入らない
- 凍結後の仕様変更は「変更」として明示し、凍結書を更新してから実装に反映する。なし崩しに混ぜない

## ② 実装（担当の選び方）

Claude Code 上ではモデルを切り替えて使う。Codex は別 CLI への発注。

| 作業 | 担当 | 使いどころ |
|---|---|---|
| 仕様設計・アーキテクチャ・難しいバグの調査 | Fable | 長時間思考が効く仕事だけ。高価なので日常実装には使わない |
| 日常の実装・リファクタ・テスト作成 | Sonnet | 迷ったらこれ |
| 凍結書が固まった実装の量産 | Codex | 凍結書を /goal 形式の発注書に変換して渡す |
| 定型作業・機械的な一括変更 | Haiku / Sonnet | 安く済ませる |
| 環境操作（サーバー起動・docker・Render デプロイ・本番 DB）・最終判断 | 人間 | AI は手順を添えて依頼し、結果を待つ |

- **担当をまたぐ引き継ぎは必ず凍結書（またはそれに準ずる文書）で行う**。会話の要約だけで渡さない
- Fable のセッションではまとまった実装をしない。設計・分析が終わったら Sonnet セッションか Codex 発注に切り替える（トークン節約）
- Codex への発注: 凍結書の「仕様・触ってよい場所・立入禁止・合格ライン・検収方法」をそのまま発注書にする。納品物の検収（③ QA）は Claude 側で行う
- DB 操作の線引き: ローカル dev/test の `bin/rails db:migrate` / `db:rollback` は AI が実行してよい。本番 DB・Render・production 環境・外部サービスに影響する DB 操作は必ず人間確認

## ③ QA（実装完了時、指示がなくても行う）

1. `bin/rubocop` と `bin/rspec` を実行し、両方グリーンにする（ルート `CLAUDE.md` の「コミット前の確認」）
2. 差分セルフレビュー（`docs/dev/CHECKLISTS.md`「コミット前」）
3. 認証・権限・外部送信・新しい依存関係に触れた変更は `docs/dev/CHECKLISTS.md`「セキュリティ」に従い `bin/brakeman` 等も実行する
4. 変更が中規模以上（目安: 3 ファイル超 or ロジック変更あり）なら /code-review を実行し、指摘に対応する
5. 実機での動作確認が必要なものは、ユーザーに確認手順を添えて依頼する（サーバー起動・docker・Render デプロイはユーザーが行う。ローカル dev/test の db:migrate / db:rollback は AI が実行してよい）

## ④ 出荷（pr-ship）

pr-ship スキルを使う（issue → コミット → PR。push と PR 作成の前にユーザー確認あり）。
PR のタイトル・本文の書式は、ルート `CLAUDE.md` の「プルリクエスト」セクションに従う（このプロジェクトで既に確立済みの書式のため、ここでは重複させない）。
